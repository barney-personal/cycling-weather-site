Cycling Weather

Methodology

How the daily ranking is built, how predictions are graded against reality, and where to look if you want to read or rerun the code yourself.

Forecast pipeline

  • Every day at 04:15 UTC a Python job pulls a 14-day forecast for 22 destinations from Open-Meteo (with wttr.in as fallback).
  • Each daily forecast row is graded as ride-clean if all of: max temp > 18°C and < 32°C, precipitation < 2 mm, max precip probability < 30%, weather code in {0,1,2,3} (clear → partly cloudy), max wind < 30 km/h.
  • Each destination's score = best_run × 100 + dry_days × 5 + median_high. A destination is a qualifier if its longest clean run ≥ 4 consecutive days (UK destinations also need median high > 20°C). Use the threshold dial to tighten or relax the bar.
  • The same Open-Meteo pull fetches hourly data (temperature, precipitation, wind, weather code) for every ride hour (06:00–20:00). This powers the per-day sparklines on destination pages (schema v2); the data.json loader supplies empty arrays when older v1 snapshots are served during the cron deploy window.
  • The full structured snapshot (daily + hourly arrays per destination) is persisted to data/cycling/forecasts/YYYY-MM-DD.json.

Actuals pipeline

  • A second daily job pulls the Open-Meteo Historical Archive for any forecast date now ≥ 2 days in the past (the archive trails real-time by ~1–2 days).
  • Persisted to data/cycling/actuals/YYYY-MM-DD.json. Idempotent — re-runs only fill gaps.
  • Actuals use a simplified ride-clean rule (no precip-probability series): max temp > 18°C and < 32°C, precipitation < 2 mm, weather code in {0,1,2,3}, max wind < 30 km/h.

Predictions vs reality

  • For every (snapshot, target-date) pair where actuals exist, we record predicted and actual temp/precip/qualify and the lead time in days.
  • Hit rate = of all days predicted ride-clean, what fraction were actually ride-clean. Bucketed by 1–3 / 4–7 / 8–14 day lead.
  • Mean temp error = mean absolute difference between predicted and actual daily high.
  • Calibration scatter plots predicted vs actual daily highs with a ±1σ residual band — closer to the diagonal means a better-calibrated forecast.
  • The history page ripens organically: it stays in an empty "still ripening" state until the daily cron has accumulated ≥14 days of matured forecasts.

Personalisation

  • The threshold dial on the homepage and plan page lets you change what "ride-clean" means: minimum temp, max wind, rain tolerance, sun preference. State is persisted to URL search params and localStorage; URL wins on conflict so a shared link reproduces exactly what a friend was looking at.
  • Personalised thresholds re-grade the forecast client-side using a TypeScript port of the Python qualifier — exact parity is asserted by a unit-test suite that checks every (destination, day) tuple.

Caveats

  • Single grid-point per destination. Local microclimates are not captured — Mallorca's Tramuntana coast and Palma can disagree on a windy day.
  • Time zones not normalised. Open-Meteo daily aggregates use the location's local timezone; we don't reconcile across hemispheres.
  • Wind is gust-style. A simple max-wind rule that doesn't differentiate a steady tailwind from punchy gusts, nor headwind direction relative to the typical loop.
  • The qualifier rule is binary. A clean run of 6 consecutive days (one short of qualifying) is treated identically to a clean run of zero — close-misses don't surface in the headline ranking.
  • "Ride-clean" is opinionated. The default rule (cycling-comfort: >18°C, <2 mm rain, <30% probability, code 0–3, <30 km/h wind) suits most road cyclists; serious racers or dry-weather-only riders should tighten thresholds via the dial.
  • Calibration view ripens slowly. A fresh deploy or a fresh destination won't show meaningful calibration until at least 14 days of forecasts have matured against actuals.
  • Forecast skill drifts with lead time. Day-1 predictions are routinely within ~1°C; day-14 can be off by 3–5°C. The hit-rate and lead-time charts on the history page surface this directly.
  • Free-tier API. Open-Meteo is rate-limited; we keep total destinations ≤ ~40 so the daily pull stays well within the budget.

Source

Everything that powers this site is in the public cycling-weather-site repo. The pipeline scripts live alongside it and run on a small cron host.

  • euro_cycling_weather.py Daily 04:15 UTC — pulls a 14-day Open-Meteo forecast per destination (daily + hourly ride-window data) and scores it against the ride-clean rule.
  • cycling_weather_actuals.py Backfills the Open-Meteo Historical Archive (lag ≈ 2 days) so we can grade matured forecasts.
  • cycling_weather_data_build.py Aggregates forecasts + actuals into the single data.json the static site fetches at runtime.
  • cycling_weather_site_refresh.sh Cron 04:45 UTC — runs the build script, commits any change to data.json, pushes to master; GitHub Pages serves the result.
